Tres formas de guardar una entidad

Referenciada

Tiene colección propia y se relaciona con las demás solo por _id, sin copiar datos de otras colecciones.

Ejemplo: cada reseña guarda el destino_id de su destino.

Embebida

No tiene colección propia. Vive como subdocumento o arreglo dentro del documento de otra entidad.

Ejemplo: los pagos van dentro de la reserva.

Híbrida

Tiene colección propia, guarda referencias por _id y además copia los pocos campos que siempre se leen, para no hacer $lookup. En MongoDB se llama patrón Extended Reference.

Ejemplo: la reserva copia el nombre y el precio del paquete.

Que una colección referenciada contenga entidades embebidas no la vuelve híbrida: Hotel es referenciada y la que va embebida es la Habitación. En toda la página, el verde de las híbridas es la mezcla del azul de las referencias y el amarillo de lo embebido.

Cómo se decidió cada caso

Preguntas que se hicieron para cada entidad

  • ¿Se consulta por sí sola o siempre junto a otra?
  • ¿Cuántas hay por cada documento padre y crecen sin límite?
  • ¿La comparten varios documentos?
  • ¿Es pesada (texto largo, vectores)?
  • ¿Cambia con frecuencia?

Un documento de MongoDB no puede pasar de 16 MB. Por eso ningún arreglo embebido puede crecer sin control, y lo que crece sin límite (reseñas, reservas, chunks) va en su propia colección.

SituaciónDecisiónEjemplo en el modelo
1 a pocos, se lee con el padre y no se comparteEmbeberPagos dentro de la Reserva
1 a muchos sin límiteColección aparte; el hijo guarda el _id del padreLa Reseña guarda destino_id
N a M con un lado acotadoArreglo de referencias en el lado acotadoEl Paquete guarda la lista de sus destinos
Se comparte o se consulta solaColección propiaDestino, Imagen
Dato que se lee mucho y casi no cambiaCopiarlo junto a la referenciaNombre del destino dentro de la Guía
Dato que no debe cambiar aunque cambie el originalCopiarlo y no sincronizarloPrecio pactado en la Reserva

Mapa del modelo

Cada flecha sale de la colección que guarda el _id y apunta a la colección referenciada. A la izquierda está el contenido que alimenta el RAG y a la derecha el negocio de la agencia; destinos y usuarios conectan las dos partes.

Pasa el cursor sobre una colección para ver qué campos la conectan con las demás. Haz clic para ir a su ficha.

Híbridas

guiasHíbrida

Entidad: Guía

Es el documento padre del RAG: los 100 documentos de texto que pide el PDF son 100 guías. Referencia a su destino y a sus imágenes, y copia lo que muestra de ellos. Es el ejemplo de modelo híbrido que da el PDF.

guias
├─ _id
├─ titulo, idioma, fecha, contenido_texto
├─ fuente { nombre, url, licencia }
├─ destino { destino_id → destinos, nombre* }
├─ imagenes [ { imagen_id → imagenes, miniatura_url*, pie* } ]
└─ etiquetas [ string ]  «Etiquetas»

  • EmbebeEtiquetas

    Lista corta de palabras. Se filtra con un índice multikey y se copia a los chunks.

  • CopiaNombre del destino; miniatura y pie de cada imagen

    Para mostrar la guía con sus fotos sin $lookup. Son datos que casi nunca cambian.

chunksHíbrida

Entidad: Chunk

El PDF exige que cada chunk sea un documento independiente. Referencia a su guía y copia idioma, fecha y etiquetas, porque el filtro previo de $vectorSearch solo usa campos indexados de la misma colección. Filtrar después con $lookup y $match reduciría los resultados.

chunks
├─ _id
├─ doc_id → guias
├─ chunk_index, estrategia_chunking, chunk_texto
├─ embedding [384], modelo, fecha_ingesta
└─ metadatos { idioma*, fecha*, etiquetas* }

  • CopiaIdioma, fecha y etiquetas de la guía

    Solo cambian si se edita la guía, y en ese caso se regeneran sus chunks. Los ocho primeros campos son los que exige el PDF; metadatos es la parte híbrida.

paquetesHíbrida

Entidad: Paquete

Referencia destinos, hoteles y proveedores (relaciones N:M) y copia sus nombres para mostrarse completo sin $lookup.

paquetes
├─ _id
├─ nombre, descripcion, duracion_dias, precio, cupos
├─ destinos [ { destino_id → destinos, nombre* } ]
├─ hoteles [ { hotel_id → hoteles, nombre* } ]
├─ itinerario [ ]  «Itinerario»
│   └─ { dia, titulo, actividades [ ] }
│       └─ { nombre, hora, descripcion }  «Actividad»
└─ transportes [ ]  «Transporte»
    └─ { tipo, desde, hasta, proveedor_id → proveedores }

  • EmbebeItinerario

    Un elemento por día del paquete. Está acotado por la duración y siempre se lee con el paquete.

  • EmbebeActividad

    Va dentro de cada día del itinerario (segundo nivel de anidación); son pocas por día.

  • EmbebeTransporte

    Tramos del paquete. Va embebido, pero guarda proveedor_id como referencia.

  • CopiaNombres de destinos y hoteles

    Casi nunca cambian. Si cambian, se actualizan con updateMany o con un Atlas Trigger.

reservasHíbrida

Entidad: Reserva

Referencia usuario, paquete y agente. Copia el nombre y el precio del paquete porque es el precio pactado: no debe cambiar si después cambia el paquete.

reservas
├─ _id
├─ usuario_id → usuarios
├─ agente_id → agentes
├─ paquete { paquete_id → paquetes, nombre*, precio* }
├─ fecha_reserva, fecha_viaje, estado, total
├─ pasajeros [ ]  «Pasajero»
│   └─ { nombre, documento, fecha_nacimiento }
└─ pagos [ ]  «Pago»
    └─ { fecha, monto, metodo }

  • EmbebePasajero

    Solo existe dentro de la reserva y guarda los datos tal como estaban al reservar.

  • EmbebePago

    Pocas cuotas. Al estar en el mismo documento, la reserva y sus pagos se actualizan de forma atómica sin necesidad de transacciones.

  • CopiaNombre y precio del paquete

    No se sincroniza a propósito: guarda lo que se pactó.

Referenciadas

destinosReferenciada

Entidad: Destino

La comparten guías, hoteles, paquetes y reseñas. Si fuera embebida en cada uno se repetiría, y habría que actualizar todas las copias.

destinos
├─ _id
├─ nombre, descripcion
└─ ubicacion { pais, region }  «País/Región»

  • EmbebePaís/Región

    Dato pequeño que se lee siempre con el destino y casi nunca cambia.

imagenesReferenciada

Entidad: Imagen

Es pesada: lleva su propio vector CLIP de 512 dimensiones con un índice vectorial aparte. Se consulta sola (búsqueda de imagen a imagen) y la misma foto sirve a la guía en español y a la guía en inglés de un destino. El archivo queda fuera de MongoDB.

imagenes
├─ _id
├─ url, miniatura_url   archivo fuera de MongoDB
├─ pie, autor, licencia
├─ embedding [512]      CLIP ViT-B/32
├─ modelo
└─ fecha_ingesta
usuariosReferenciada

Entidad: Usuario

Existe por sí mismo. Sus reservas y reseñas crecen con el tiempo, así que son ellas las que guardan su _id.

usuarios
├─ _id
├─ nombre, email, idioma_preferido, fecha_registro
└─ historial_consultas [ máx. 50 ]  «Historial de consultas»
    └─ { texto, endpoint, fecha }

  • EmbebeHistorial de consultas

    Lo pide el PDF. Solo se guardan las últimas 50, con $push y $slice (patrón Subset), para que no crezca sin límite.

hotelesReferenciada

Entidad: Hotel

Lo usan muchos paquetes (relación N:M).

hoteles
├─ _id
├─ nombre, estrellas, direccion
├─ destino_id → destinos
└─ habitaciones [ ]  «Habitación»
    └─ { tipo, capacidad, precio_noche }

  • EmbebeHabitación

    Pocos tipos por hotel; no se consulta sin el hotel.

proveedoresReferenciada

Entidad: Proveedor

Lo usan muchos paquetes y sus tramos de transporte.

proveedores
├─ _id
├─ nombre, tipo   aerolínea, transporte terrestre, operador
└─ contacto { email, telefono }
resenasReferenciada

Entidad: Reseña

Crece sin límite. Si fuera embebida, empujaría al destino hacia el tope de 16 MB por documento. Además se consulta paginada.

resenas
├─ _id
├─ usuario_id → usuarios
├─ destino_id → destinos
└─ calificacion (1 a 5), comentario, fecha
agentesReferenciada

Entidad: Agente

Pocos agentes referenciados desde muchas reservas. Si fuera embebido, se repetiría en cada reserva.

agentes
├─ _id
└─ nombre, email, codigo, sede

Convención propuesta: nombres de colección en plural, en español y sin tildes ni ñ (resenas, guias, imagenes), para evitar problemas de codificación en scripts y URIs.

En un modelo relacional, cada relación N:M necesitaría una tabla intermedia (Guía_Imagen, Paquete_Destino, Paquete_Hotel, Guía_Etiqueta). Aquí se resuelven con arreglos. Esto sirve para la comparación con el enfoque relacional que pide el informe final.

Embeber vs. referenciar

AspectoEmbeberReferenciar
LecturaUna sola consulta trae todoHace falta $lookup o una segunda consulta
EscrituraAtómica, porque es un solo documentoCambiar varios documentos de forma atómica requiere una transacción
DuplicaciónPuede repetir datosCada dato está en un solo lugar
CrecimientoLimitado por los 16 MB; solo sirve para arreglos acotadosSin límite
Acceso independienteHay que entrar por el documento padreSe consulta directamente
Actualizar un dato compartidoHay que actualizar cada copiaSe actualiza una sola vez
ÍndicesSobre campos del padre (multikey en arreglos)Cada colección tiene sus propios índices
Cuándo usarlo1 a pocos, se lee con el padre y no se comparte1 a muchos sin límite, compartido, pesado o consultado solo
Ejemplo en el modeloPagos y pasajeros dentro de la reservaReseñas de un destino; imágenes

El modelo híbrido combina ambos. La referencia mantiene una sola fuente de verdad, y la copia de los pocos campos que siempre se leen evita el $lookup en la consulta frecuente. El costo es mantener esas copias; por eso solo se copian datos estables o que no deben cambiar.

Pendiente de confirmar

Propuestas que todavía no están en el modelo

  1. imagenes.destino_id. En la búsqueda de imagen a imagen el resultado es una imagen, y hay que saber de qué destino es. Sin este campo se resuelve con un $lookup a guias por imagenes.imagen_id.
  2. chunks.metadatos.destino_id. Permitiría filtrar por destino dentro de $vectorSearch. Sería útil en el caso de prueba "Compara las opciones de transporte entre Cartagena y Santa Marta".
  3. destinos.calificacion_promedio y destinos.total_resenas (patrón Computed). Evitan recalcular el promedio en cada consulta. Se mantendrían con el Atlas Trigger opcional del PDF, lo que de paso le daría uso a ese punto.

Riesgos para la sustentación

  • Entidades débiles. Etiquetas y País/Región son las más fáciles de cuestionar dentro de las 20, porque son datos pequeños sin identidad propia. Defensa: en un modelo relacional serían tablas (Etiqueta con su tabla intermedia Guía_Etiqueta, y País con relación 1:N a Destino); en MongoDB se embeben porque son pequeñas, se leen siempre con su padre y casi no cambian. Si el profesor no las acepta, hay reemplazos posibles: Amenidad (en Hotel) o Política de cancelación (en Paquete).
  • RAGAS (opcional). El ejemplo del PDF guarda id_consulta: ObjectId en la colección evaluaciones, pero en este modelo las consultas viven embebidas en Usuario. Si se hace RAGAS, hay que decidir a qué apunta ese id.
